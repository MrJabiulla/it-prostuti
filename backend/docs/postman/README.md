# Postman collection

Import both files into a local Postman workspace:

- [Prosthuti.postman_collection.json](Prosthuti.postman_collection.json)
- [Prosthuti-Local.postman_environment.json](Prosthuti-Local.postman_environment.json)

Select **Prosthuti — Local**. `base_url` defaults to
`http://127.0.0.1:8000/api/v1`, without a trailing slash. Start the backend using
its existing [local setup](../../README.md). Keep the Postman cookie jar enabled
and use one hostname consistently. No bearer token is needed.

The [API inventory](API-INVENTORY.md) lists all **62 backend route operations**.
The collection has three top-level folders:

```text
Prosthuti API — Admin, Web and Mobile
├── Admin (56 requests)
│   ├── Authentication
│   ├── Profile
│   ├── Catalogue
│   ├── Content
│   └── Media
├── Web (40 requests)
│   ├── Authentication
│   ├── Profile and dashboard
│   ├── Subjects, chapters and lessons
│   ├── Questions, exams and papers
│   ├── Revision and routine
│   ├── Practice and exam attempts
│   └── Media download
└── Mobile (40 requests)
    └── Same student API groups as Web
```

There are **136 request entries**, representing **87 unique concrete method/path
pairs** and **59 directly exposed backend route operations**. The CSRF and Google
nonce routes are called internally by scripts. The compatibility-only explicit
Google-link route is omitted from this simplified collection. Backend inventory
now contains 62 operations. Web and Mobile use the same endpoints.

Each Authentication folder contains only **Registration**, **Login**,
**OTP Verification**, **Google Login / Registration** and **Logout**.

All folders share the selected environment, cookie jar and collection variables.
Switch accounts with logout/login when testing different roles. Mobile currently
uses the same session-cookie and CSRF contract; this organization does not add
mobile-specific routes or bearer-token authentication.

Requests include JSON bodies, optional disabled filters, multipart upload,
expected status checks and saved response IDs. These are request templates,
not a full automated collection run; choose the actions you intend to perform.
Admin writes and deletes change data.
No live credentials, cookies, OTPs or uploaded files are included.

## Sign in

1. Set `email` and `student_name` in the selected environment.
2. Send **Registration** with email/name for a new account, or **Login** with
   email for an existing account. Both use the same passwordless OTP endpoint.
3. Get the six-digit code from the configured mailer and set `otp_code`. With
   local `MAIL_MAILER=log`, it is in `backend/storage/logs/laravel.log`.
4. Send **OTP Verification** in the same cookie session. Registration's name is
   applied when the account is created. Existing accounts are reused, including
   those originally registered by Google; names and progress are preserved.
5. Use the appropriate client folder. **Logout** ends the session immediately.

The collection fetches `/auth/csrf` internally before mutations and sets
`X-CSRF-TOKEN`. No separate CSRF action or manually copied token is needed.
Cookies are managed by Postman. Sessions default to **30 idle days**, renew with
activity and persist across browser restarts. OTP codes still expire in 10
minutes. The collection's folders share the current session.

For **Google Login / Registration**, leave `google_credential` empty on the first
Send. Its script initializes `google_nonce` and `google_client_id`, then skips
the login POST. Use these values in Google Identity Services to obtain a real
ID token, set `google_credential`, and Send again. Do not refresh the nonce after
minting the token. For a new attempt, clear the credential and repeat. A real
Google identity credential cannot be generated by Postman itself; the app's
Google sign-in integration will handle this interaction when implemented.

Verified Gmail/Workspace sign-in automatically opens the matching existing
account or creates a new student. An unlinked non-Google-hosted email must first
prove ownership via OTP; Google sign-in then links it in that matching signed-in
session. Conflicting Google identities return 409; disabled accounts return 403.

## IDs, filters and requests

Collection variables hold IDs captured from successful responses. Keep these
IDs out of the environment unless deliberately overriding them, because an
environment value takes precedence over collection variables.

- Run **List subjects → Get subject and chapters → Get chapter topics and
  completion → Get lesson** to populate the reading IDs.
- **List questions**, **List exams**, **List papers** and **List current affairs**
  capture their first result IDs. Select a different returned ID manually when
  needed. Empty lists do not produce an ID.
- Set `date`, `date_from`, `date_to`, `month`, `year`, `page` and `per_page` as
  needed. The default October 2026 month matches the local demo content.
- Optional filter query parameters are disabled in the Params tab. Enable them
  selectively. `revision_type` is `lessons` or `questions`; paper `solutions=1`
  deliberately reveals study answers.
- Bookmark requests accept `saved=false` to remove bookmarks. Lesson note
  accepts `body=null` to clear the note.
- Numeric ID placeholders in JSON are encoded as strings; Laravel's existing
  integer validators accept numeric strings. IDs must refer to actual records.

## Attempts

**Create attempt** generates `request_id` once if its collection value is empty.
It keeps that UUID on retries, including failed/uncertain network responses.
Clear `request_id` only when intentionally starting a different attempt; complete
the active attempt first. The server permits only one active attempt per user.

The response sets `attempt_id` and `attempt_item_id`. **Save answer batch** uses
snapshot item IDs, not catalogue question IDs. Choices are zero-based; null means
unanswered. Save answers before **Submit attempt**. The server owns timers,
scoring and penalties; practice answers cannot change after being revealed.

Alternative Create attempt bodies (use the same stable `request_id` rule):

```json
{
  "request_id": "{{request_id}}",
  "mode": "exam",
  "paper_id": "{{paper_id}}"
}
```

```json
{
  "request_id": "{{request_id}}",
  "mode": "exam",
  "chapter_id": "{{chapter_id}}",
  "chapter_test": true,
  "count": 20
}
```

```json
{
  "request_id": "{{request_id}}",
  "mode": "practice",
  "current_affair_id": "{{current_affair_id}}",
  "count": 10
}
```

A chapter test requires all chapter lessons completed. Ordinary custom practice
also accepts subject/chapter/topic/exam filters, status `all/new/wrong/skipped/due/saved/mistakes`
and count 1–100. Paper attempts use the complete ordered paper and stored rules.

## Admin and files

Sign in with an existing administrator account using the same authentication
flow. The API does not provide a role-escalation request. Follow the backend's
trusted `app:make-admin` command only when intentionally granting access.

Create parent records before children: subject → chapter → topic; institute →
post; exam; then lesson/question/paper. Admin creates set separate `admin_*_id`
variables, so student list reads do not silently retarget admin edits/deletes.
If using existing records, inspect the lists and set these variables explicitly.
Create a unique slug on subsequent catalogue creates. Each topic has at most
one lesson. Updates replace the submitted children, so fetch details first.
Content examples start as unpublished demo records. There are no content delete
routes: unpublish using the full update payload. Referenced catalogue deletes
return 409.

For **Upload media file**, select a local JPEG/PNG/WebP/PDF in Body → form-data →
file. Maximum size is 10 MiB. Postman sets the multipart Content-Type boundary.
Publication starts false. Upload captures both `admin_media_id` and `media_id`;
use **Set media publication** for student access. **Download media file** streams
the file; use Send and Download. R2 requires the existing backend configuration.

## Scope and validation

This collection documents the implemented backend; it does not connect Student
Web to it. See the inventory for API/UI contract differences and absent routes.
The source of truth is `backend/routes/web.php` plus the controller validators.
The existing OpenAPI document is an inventory, not exhaustive response schemas.

The collection follows the [official Postman v2.1 schema](https://schema.getpostman.com/json/collection/v2.1.0/collection.json).

Verified on 2026-10-03:

- Official collection v2.1 schema and embedded request scripts are validated.
- Authentication changes preserve the non-authentication request definitions.
- Backend suite: 43 tests, 245 assertions passed, including registration name,
  OTP/Google account reuse, access protection and 30-day cookie/database expiry.
- Tests use `prosthuti_test`; external Google/email services are faked. Real
  email delivery, Google sign-in and R2 were not exercised.
- Postman itself was not used for a live end-to-end run.

## Device input

Open **OTP Verification** or **Google Login / Registration** and select **Body > raw > JSON**. The `device` object contains the input fields. Edit `device_name`, `os_version`, and `app_version` in collection variables. Keep `device_id` stable while testing the same installation; generate a different UUID to simulate another device. Web/Admin use `web`; Mobile defaults to `android` and can be changed to `ios` in the body. Device input is submitted during verification/login, not OTP request. Session tokens remain internal in the cookie jar. Tracking is enabled; device limits are not enforced.
